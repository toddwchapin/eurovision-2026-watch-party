# Party integrity release (#89–#94)

## Architecture and contract

The app remains plain static HTML/CSS/JS. No bundle, framework or runtime npm install is required. `shared/config.js` is the only Firebase/year config; `acts-data.js` owns the roster, running orders and stage names. `shared/scoring.js` validates/filter scores; `shared/storage.js` namespaces local data; `shared/session.js` owns Anonymous Auth, party membership, subscriptions and acknowledged per-act writes; `shared/dialogs.js` provides focus containment/return. Page scripts own rendering.

New parties use `2026/parties/CODE/{meta,members,users}`. `meta` contains immutable host UID, creation timestamp and seven-day invite expiry. Only an authenticated exact-code metadata lookup is readable before joining; party listings and user data are not. Possession of a live code is the admission credential. Members may read the party’s users and write only their own name/votes/epochs. A host has no power to edit another guest’s ratings. Expiry prevents new admission; existing members retain access to their records. Clients show recovery when an invite is expired. Do not advertise invite codes publicly.

Complete scores are integer 0–5, five fields plus derived sum, string note <=200, reset epoch and server timestamp. Rules reject unknown stages, acts outside that stage’s roster, unknown fields, partial/fractional/out-of-range ratings, forged timestamps and inconsistent sums. When the roster changes, update the stage/act allowlist in `database.rules.json` at the same time; tests should exercise the changed roster. Funniest/superlatives are derived from member-readable validated votes, not a writable shared winner record.

## Sync, conflict and deletion policy

Only the edited act is written. No whole-stage replay and no automatic upload on listener attach. Pending objects are namespaced by party, Firebase auth UID, contest and act, with operation ID and epoch. They remain pending until the write promise is acknowledged; errors never count as Shared. Same-act concurrent edits use **last server-accepted write wins**, including an older offline edit accepted later. Distinct acts never replace each other. Drafts remain local and do not count in aggregates.

The SDK writes only while connected; in-flight writes that disconnect may remain queued by Firebase. Reset/leave wait for in-flight writes; therefore destructive actions require reconnection. Reset atomically increments the selected contest’s epoch and deletes that contest’s votes. Own optimistic SDK events cannot clear durable local pending/votes/drafts during reset/leave: a durable pre-operation snapshot is retained until acknowledgement or rejection. A rejected operation restores the view from untouched active caches, without replaying a snapshot over another tab’s acknowledged writes or committed reset. Only acknowledged destruction cancels pending and drafts. Destructive updates wait for a definitive SDK result rather than treating a timeout as rejection (a queued write can still commit later). Other tabs have separate SDK connections and receive committed server epochs, not the initiating tab’s optimistic/rollback events. Stale pending operations are dropped when committed epochs change, and rules reject old-epoch writes even from tabs disconnected during reset. Leave atomically clears shared name, all votes and membership while incrementing every epoch in one party-root multipath update; epoch tombstones are deliberately retained so a later rejoin cannot resurrect stale offline operations. The owner write grant itself requires every existing stage tombstone to remain numeric and nondecreasing, including deletes of an epoch, its subtree or the whole user (delete skips validation). Vote validation uses the post-update epoch. Pages exclude nameless tombstones from guests. Local result snapshots are archived under the same party/UID/stage with kind `left-votes` on leave, but pending queues/drafts are canceled. Archives are not automatically restored/uploaded on rejoin; download before leaving or recover the archive deliberately from browser storage. Auth changes stop syncing until reload; a new identity gets different local keys.

Essential subscription errors are tracked separately from write errors; empty/successful queue flushes cannot erase them. Save/readiness stay disabled until the failed subscription recovers or Retry reloads/reconnects. Local-storage failures display an error; download results before closing. A disconnected initial load cannot authenticate/admit a new guest; reconnect and Retry. Drafts and prior local snapshots are retained even when admission fails. The app is not a service worker/PWA and does not promise offline loading of uncached HTML/SDK files.

## Legacy policy — no unauthorized claims

Legacy generated user IDs are not Firebase identities. Never reinterpret them as auth UIDs, automatically claim a legacy remote user, or migrate a remote record from an untrusted browser-provided ID. Legacy parties with no secure metadata are inaccessible under the new rules, and cannot be silently overwritten/claimed through the client. Create a fresh party code. Before release an authorized operator must export the old database with administrative tooling into private storage. Keep that backup and legacy remote data; these rules simply deny client access to the old records. Do not include the export in git.

Old `ev_2026_votes_*_v1` / `ev_2026_votes_v1` local keys are left untouched; new keys start `ev:2026:v2:PARTY:AUTH_UID:STAGE:KIND`. No legacy votes are automatically uploaded or assigned to a different party. A user can export their old local JSON from browser storage before upgrading, then deliberately re-enter complete scores in the new party. If an operator later implements an import, it must be explicit, owner-confirmed, validated, and attributable; incomplete legacy zeros cannot be inferred as intentional selections.

## Operator checklist (not executed by this implementation)

1. Run `npm ci`, `npx playwright install --with-deps chromium`, `npm test`, and `npm run test:regressions` on a checkout containing the baseline commit. Review the diff and test artifacts. Tests explicitly pass `--project demo-eurovision --config firebase.test.json`; **never use `.firebaserc` as the test project**.
2. Export production legacy data privately. Prepare fresh invites and tell attendees the old codes/local records are not automatically migrated.
3. In the intended Firebase project, enable **Authentication → Sign-in method → Anonymous** and verify authorized host domains. This is a deployment prerequisite, not a client flag or an action the test suite performs.
4. Optionally provision Firebase App Check with reCAPTCHA, add `appCheckSiteKey` to `shared/config.js`, load/allow its provider domains in CSP, register test/dev tokens appropriately, and check metrics before enabling enforcement. App Check is off by default and skipped in emulator mode. Enabling enforcement before distributing a configured client will deny requests.
5. Coordinate the static client and database rules release during a maintenance window. Old clients and these rules are incompatible. Rules should lead (fail closed), then serve the new HTML/shared modules and invalidate old cached pages. There is no automatic deploy command in the test/CI job. Inspect the explicit target project before any manual deployment.
6. Verify fresh hosting, invite joining, own-write permissions, scoreboard/trivia, and reset with operator-approved test identities after deployment; never run emulator tests against production. Monitor permission/auth errors and queue acknowledgment states.

## Rollback

Stop distribution and preserve a private export of newly created data before rollback. Revert client and rules together only after security review: blindly restoring baseline rules would reopen unauthenticated foreign writes. Prefer a deny-all maintenance rule and fix-forward client/rules. Never delete epoch tombstones or reinterpret legacy owners. Anonymous Auth can remain enabled. If App Check enforcement caused denial, disable enforcement temporarily with operator approval rather than adding bypasses to code.

## Development/CI

Prerequisites: Node 24.12.0 (CI pin; Firebase 13/rules testing 6 require >=24.12.0), Java 21, Python 3, Chromium installed through Playwright. `npm test` starts and stops Auth/RTDB emulators, then runs unit, rules and browser gates. On this Mac the runner recognizes Homebrew `openjdk@21` without modifying global Java configuration. Browser HTTP and WebSocket traffic is restricted to loopback; Firebase SDK scripts are served from the installed package, fonts are blocked, and any other outbound app request fails the test. Production app CDN SDK version is matched to that package’s major version. Dependencies are development-only; do not publish `node_modules`, tests, private exports or emulator logs with static assets.

`npm run test:regressions` executes the baseline’s actual score/reset functions in a VM with deterministic DOM/database doubles, verifies the current functions pass, runs deliberate blank/reset sabotage mutations, and runs the real rules suite against baseline rules on the demo emulator. Expected baseline failures are evidence, not a failing CI job. Scratch outputs live under `~/.hermes/cache/scratch`.

CI runs the same gates on Node 24.12.0/Java 21 and uploads trace/screenshot/log artifacts on failure. Remote CI is not verified until the parent publishes a commit/PR. Chromium synthetic keyboard/desktop coverage is not a physical iOS VoiceOver/WebKit certification. Do a device smoke test before the event. `npm audit` can report transitive development-tool vulnerabilities; evaluate them separately, avoid force-downgrading Firebase to obsolete releases, and do not imply a clean audit unless the command confirms it.
